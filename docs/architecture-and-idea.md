# بازطراحی معماری کلادک — نسخه ۲ (مهندسی معکوس)

این سند بر اساس سه چیز نوشته شده: داده‌های واقعی بازار (Flippa، Acquire.com)، الگوهای شکست مارکت‌پلیس‌ها (تمرکز باریک به‌جای پهن)، و تصمیم‌هایی که خودت گرفتی (تأیید یک‌ماهه، فازبندی، تعریف حوزه‌ای).

---

## ۱. مهندسی معکوس نسخه‌ی قبلی — چی خوب بود، چی مشکل داشت

**نقاط قوت کد قبلی:**
- ساختار کامپوننت React تمیز و تفکیک‌شده (NDA، VDR، Valuation، Notification جدا از هم)
- تلاش درست برای امنیت: iframe sandbox خالی، واترمارک PDF سمت سرور (نه سمت کلاینت)

**مشکلات جدی:**
1. هیچ بک‌اند واقعی وجود نداشت — همه‌چیز روی داده‌ی mock سوار بود؛ مسیرهایی مثل `/api/listings` یا `/api/ai/match` هیچ‌وقت پیاده نشدن.
2. تأیید («Verified») فقط یک بج نمایشیه، بدون اتصال به منبع داده‌ی واقعی — یعنی هرکسی می‌تونه ادعا کنه.
3. `AiMatchmaker` امتیاز تطبیق رو با `Math.random()` می‌ساخت — یعنی «هوش مصنوعی» کاملاً جعلی بود.
4. هیچ مدل درآمدی تعریف نشده بود (نه حق اشتراک، نه کارمزد معامله).
5. فیچرهای سنگین (اتاق داده‌ی امن، امضای الکترونیک، ماشین‌حساب ارزش‌گذاری) از روز اول ساخته شدن — قبل از اینکه حتی یک فروشنده‌ی واقعی وجود داشته باشه.
6. طراحی برای «همه‌ی حوزه‌ها همزمان» بود، نه یک حوزه‌ی اول برای اثبات مدل.

---

## ۲. چیزهایی که نگه می‌داریم
- کامپوننت‌های پایه‌ی UI: `ListingCard`، `ListingGrid`، `LeadForm` — قابل استفاده‌ی مجدد
- ساختار NDA و VDR — ولی منتقل به فاز ۲
- منطق واترمارک PDF سمت سرور — ایده درست بود، فقط زودهنگام ساخته شده

## ۳. چیزهایی که فعلاً حذف می‌کنیم
- `AiMatchmaker` با امتیاز جعلی — حذف کامل تا وقتی داده‌ی واقعی برای محاسبه‌ی تطبیق داشته باشیم
- `ValuationCalculator` با ضرایب دلبخواهی — یا حذف کامل، یا با یک هشدار خیلی واضح که «فقط تخمین اولیه‌ست، نه مشاوره‌ی مالی»
- چندحوزگی از روز اول — محدود به یک حوزه در فاز ۱

---

## ۴. چیزهایی که اضافه می‌کنیم

### الف) موتور تأیید (Verification Engine) — جایگزین بج‌های نمایشی

جریان کار:
1. فروشنده ثبت‌نام می‌کند
2. اتصال **اجباری** به حداقل یک منبع داده‌ی واقعی: کلید Stripe فقط‌خواندنی برای درآمد، یا OAuth با Google Analytics/Search Console برای بازدید
3. سیستم به‌صورت خودکار یک نمای ۳۰ روزه از داده می‌کشد (همون دوره‌ی آزمایشی که خودت پیشنهاد دادی)
4. بررسی دستی UI/UX و محتوا توسط تیم بررسی (فعلاً خودت)
5. وضعیت نهایی: در انتظار / تأیید‌شده / رد‌شده
6. فقط بعد از تأیید، امتیاز و درجه (A/B/C) محاسبه می‌شود — نه قبلش

### ب) موتور امتیازدهی قابل‌تنظیم برای هر حوزه

به‌جای فرمول ثابت برای همه‌ی حوزه‌ها، هر حوزه یک «rubric» جدا در دیتابیس دارد (نه هاردکد در کد) — یعنی بدون تغییر کد می‌شه معیار حوزه‌ی جدید تعریف کرد.

نمونه‌ی ساختار داده:
```json
{
  "category": "SaaS",
  "criteria": [
    { "key": "verified_mrr_growth", "weight": 30 },
    { "key": "churn_rate", "weight": 20 },
    { "key": "traffic_trend_6mo", "weight": 20 },
    { "key": "ui_ux_review_score", "weight": 15 },
    { "key": "time_on_market", "weight": 15 }
  ],
  "grade_bands": { "A": 85, "B": 65, "C": 40 }
}
```
حوزه‌ی سلامت یا هنر همین ساختار رو داره، فقط با معیار و وزن متفاوت — این جواب مستقیم به «هر حوزه یه تعریف» است.

### ج) مدل درآمدی (بر اساس الگوی اثبات‌شده‌ی بازار)
- ثبت‌آگهی رایگان (اصطکاک کم برای فروشنده)
- اشتراک خریدار: سطح رایگان (مرور محدود) + سطح پولی (تماس مستقیم، دسترسی کامل به داده‌ی تأییدشده)
- کارمزد موفقیت معامله: ۳ تا ۵ درصد، فقط روی معاملات واقعاً بسته‌شده

### د) نقشه‌راه فازبندی

**فاز ۰ (الان):** انتخاب یک حوزه‌ی اول — پیشنهاد من: همون حوزه‌ای که خودت الان یک پروژه‌ی واقعی توش داری، تا اولین لیستینگ و اولین تأیید دستی رو با نمونه‌ی واقعی خودت تست کنی.

**فاز ۱ (MVP):**
- ثبت‌نام فروشنده + اتصال Stripe/GA (تأیید فعلاً دستی توسط خودت)
- لیست ساده + فرم تماس خریدار
- بدون NDA، بدون VDR، بدون پرداخت آنلاین — این‌ها زودهنگامن

**فاز ۲ (بعد از اولین ۵ تا ۱۰ معامله‌ی واقعی):**
- خودکارسازی تأیید (اتصال API واقعی)
- سیستم اشتراک خریدار + پرداخت
- امضای الکترونیک واقعی (سرویس خارجی، نه فقط تایپ اسم)

**فاز ۳:** گسترش به حوزه‌ی دوم و سوم، فقط اگه فاز ۱ و ۲ در حوزه‌ی اول واقعاً تقاضا رو ثابت کرده باشن.

---

## ۵. چیزهایی که از نسخه‌ی سوم می‌گیریم

این نسخه یک پیشرفت واقعی داشت: بالاخره کنترل دسترسی سند به‌درستی پیاده شده بود. این الگو رو نگه می‌داریم و توی معماری خودمون قرار می‌دیم.

### الف) الگوی دسترسی به سند (از فاز ۲ به بعد)
- قبل از دادن لینک سند، سیستم چک می‌کند که NDA مربوط به همان خریدار و همان لیستینگ واقعاً «تأییدشده» باشد — نه فقط «امضاشده».
- لاگ بازدید (audit log) **قبل از** ارائه‌ی لینک ثبت می‌شود، نه بعدش — یعنی حتی اگر دانلود قطع شود، رکورد بازدید از دست نمی‌رود.
- لینک نهایی همیشه کوتاه‌مدت باشد (signed URL چند دقیقه‌ای).

### ب) محافظت‌های پایه که باید از فاز ۱ باشند، نه فاز ۲
- **اعتبارسنجی ورودی (مثل Zod):** روی هر فرم عمومی (فرم تماس خریدار، ثبت‌نام فروشنده) از روز اول — هزینه‌اش کمه و جلوی داده‌ی خراب رو می‌گیره.
- **Rate limiting:** روی فرم‌های عمومی از فاز ۱، برای جلوگیری از اسپم و سوءاستفاده — این هم ارزون و مهمه، برخلاف NDA/VDR که واقعاً می‌تونن صبر کنن.

## ۶. قانون طلایی: هیچ آمار یا ادعای جعلی

این نکته دومین‌بار است که در بازبینی کد ظاهر می‌شود (بار اول بج‌های «Verified» بی‌پایه، بار دوم آمار اعتماد جعلی و برچسب غلط «Legally binding» روی امضای تایپی) — پس به‌عنوان یک قانون ثابت پروژه ثبت می‌شود، نه فقط یک نکته‌ی موردی:

- هیچ عدد، آمار، یا گواهی (مثل «۱۰۰۰+ کاربر»، «SOC 2 Type II»، «ISO 27001») روی صفحه‌ی عمومی نمی‌رود مگر واقعاً درست باشد.
- هیچ برچسب حقوقی («Legally binding») روی چیزی گذاشته نمی‌شود که واقعاً از نظر قانونی الزام‌آور نیست.
- اگر صفحه‌ای به عدد واقعی نیاز دارد ولی هنوز عدد واقعی نداریم، یا خالی می‌ماند یا با عبارت صادقانه پر می‌شود (مثلاً «تازه شروع کردیم»)، نه با عدد ساختگی.

## ۷. یک باگ فنی که باید از اول درست ساخته شود

در نسخه‌ی سوم، شناسه‌ی کاربر همه‌جا به‌صورت ثابت (`'user-demo'`) هاردکد شده بود — یعنی اگر دو خریدار واقعی هم‌زمان روی یک لیستینگ NDA امضا کنند، به‌خاطر محدودیت یکتای دیتابیس با خطا مواجه می‌شوند. وقتی احراز هویت واقعی در فاز ۱ پیاده می‌شود، باید از همان ابتدا شناسه‌ی واقعی کاربر از سشن گرفته شود، نه یک مقدار ثابت موقت که ممکنه فراموش بشه و تا production بمونه.

## ۸. حوزه‌ی انتخاب‌شده برای فاز صفر: Micro-SaaS

بر اساس تقاضای واقعی بازار (نه ترجیح شخصی)، تصمیم گرفته شد فاز صفر روی **Micro-SaaS** (ابزارهای نرم‌افزاری کوچک با درآمد اشتراکی، تمرکز باریک روی یک کار خاص) متمرکز بشه.

شواهد پشتوانه‌ی این تصمیم:
- رشد ۷۳.۵٪ حجم معاملات SaaS روی Flippa در سال ۲۰۲۵
- SaaS «به‌مراتب محبوب‌ترین مدل کسب‌وکار» روی Acquire.com
- SaaS حدود ۵۸٪ کل معاملات M&A نرم‌افزاری (نسبت به زیر ۴۰٪ پنج سال پیش)

ویژگی لیستینگ‌های ایده‌آل فاز صفر: تمرکز باریک روی یک کار خاص (نه ابزار همه‌کاره)، نرخ ریزش کاربر پایین، درآمد اشتراکی قابل پیش‌بینی.
